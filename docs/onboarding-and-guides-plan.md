# Onboarding in the apps, guides on the website

A plan for two things that are really one thing: the first-run explanation
inside every Tiko app, and the written guide for that app on tikotalks.com.

## The idea in one line

**Write each app's explanation once, render it twice.** The same authored
content becomes the first-run flow on the device and the guide page on the
website, so the two can never drift and nobody writes the app's story twice.

---

## What is there today

Findings from the codebase, not assumptions.

| Thing | State |
| --- | --- |
| Onboarding, anywhere | **None.** `grep -rn "onboard\|tutorial\|firstRun\|welcome"` across TikoKit and every app's sources returns nothing. |
| Shared iOS shell | `TikoAppShell` — 41 TikoKit components, mature. Already owns splash, settings, account, parent gate. |
| Shared Android shell | `tikokotlinkit` has **two files**. Effectively nothing. TIKO-025 already owns the migration. |
| Shared web shell | `packages/ui` has `app-config`, `TikoAppHeader`, `TikoAppTheme`. Thin. |
| App i18n | 547 distinct English strings across 12 apps; 89 of them "core". Translated **by English string, not by key**, so "Cancel" is translated once for eleven keys. |
| Locale registry | 54 locales, generated by `tools/locales.mjs` into both Swift and TS so the platforms cannot disagree. |
| Locale coverage | Core: **54/54 complete**. Everything else: `mt` 209/547, `es` 207, `nl` 206, `de` 205, `fr` 204, `pt` 103, and **the other 47 locales sit at 88/547**. |
| Website | Vue, `apps/website/web`. Copy in 9 locales (`en nl de fr es pt it mt hy`). |
| Website content model | `i18n/content.model.ts` — a page is an opening plus sections, each carrying *either* prose, points, steps, or questions. Explicitly built so pages are "translatable without touching a component". |
| Website docs | `docsContent.ts` — hardcoded English, developer-facing, not in the locale system. |
| Per-app metadata | `content/appUniverse.ts` — `features`, `useWhen`, `moment`, `whySmall`, screenshots. Rich, and TIKO-061 is already moving its prose into the copy bundles. |

### Two gaps that block onboarding before it starts

1. **Talk and Coloring are not in the i18n system at all.** `TikoAppKey` lists
   twelve apps; `apps/` ships fourteen iOS targets. Talk has no entry in
   `source-en.json` and no `case talk` in `TikoAppKey`. Onboarding for those two
   cannot be translated until they are registered.
2. **Sequence is an empty shell** — `apps/sequence/ios/Sources/` contains only
   `Assets.xcassets`. It gets a guide when it gets an app.

## The content shape

One file per app, platform-neutral, in a new `packages/guides/`:

```jsonc
{
  "app": "globe",
  "version": 1,              // bump to re-show onboarding after a real change
  "intro": {
    "title": "A whole world you can turn with one finger",
    "body": "Spin the Earth, tap a country, and hear its name."
  },
  "steps": [                 // 3–5. Each is one screen in-app, one section on web
    { "id": "turn",  "title": "Turn the Earth",  "body": "…", "media": "globe-turn" },
    { "id": "tap",   "title": "Tap a country",   "body": "…", "media": "globe-tap" },
    { "id": "modes", "title": "Five ways to look", "body": "…", "media": "globe-modes" }
  ],
  "tips": [ … ],             // web only
  "faq":  [ … ]              // web only
}
```

**In-app renders `intro` + `steps`, and nothing else.** Web renders everything.
That split is the whole reason a grown-up gets a five-screen flow on the phone
and a full page on the site without anyone writing both.

The `steps` shape is deliberately the same as the website's existing
`ContentStep`, so the site's renderer already knows how to draw it.

### Where it goes

Follows the pattern the repo already uses everywhere (`TikoI18nGenerated.swift`,
`TikoLocales.generated.swift`, `TikoArlezProjects.generated.swift`):

```
packages/guides/content/<app>.json      ← authored, English
tools/generate-guides.mjs               ← one generator
  ├→ packages/tikokit-ios/Sources/TikoKit/TikoGuides.generated.swift
  ├→ packages/guides/src/bundles.generated.ts   (web apps + website)
  └→ workers/translations-api/data/…            (for the translation route)
```

Add `--check` to the generator and hang it off `generated:check`, like every
other generator in `package.json`.

## In-app onboarding

### Rules it has to obey

These are constraints from the product and from this codebase, not preferences.

- **It is for the grown-up, not the child.** Tiko apps open with no account
  ceremony and are useful immediately. Onboarding must never become a wall a
  child cannot get past. One tap dismisses it, always, from every screen.
- **Once, then never.** Keyed on `@AppStorage("tiko.guide.<app>.seenVersion")`,
  matching the existing `tiko.*` storage convention. Re-openable from Settings
  ("How this app works") so it is never lost.
- **Skipped entirely in screenshot mode.** `TikoAppShell.task` already returns
  early on `TikoScreenshotMode.isActive`. If onboarding is not behind that
  check, every App Store screenshot becomes a picture of the onboarding.
- **A sheet, not a fifth popup.** TikoKit's own note: *"One popup at a time:
  PopupView will not swap a presented card for a new one in the same update."*
  The shell already owns four. Globe hit this exact bug — its country list
  failed to open about one run in ten — and fixed it with `.sheet` plus
  `TikoPopupCard`. Onboarding takes the same route.
- **Reduce-motion respected.** The shell already reads
  `accessibilityReduceMotion`; a stepped flow must not animate past it.
- **No network.** Cards, Globe and the rest work offline. So does this.

### Where it hooks

`TikoAppShell`, after the splash resolves — the one place all twelve apps
already share. An app opts in by passing its guide key; passing nothing means no
onboarding, so nothing changes for an app until it is ready.

## Website guides

- New route per app. `/apps/<slug>/guide` keeps it beside the app's own page.
- Rendered by the **existing** `ContentSection` renderer — `steps` and `points`
  are already in the model, so this is content, not new components.
- **Depends on TIKO-061**, which is in progress and moves app prose out of
  `appUniverse.ts` into the locale bundles. Building guides before that lands
  means writing them twice.
- The app deep-links to it: "Read the full guide" opens the guide in the
  language the app is set to.

## Translation — the part that will actually hurt

This is the risk, so it gets its own section.

The existing pipeline translates **English strings**, which is exactly right for
"Cancel" and exactly wrong for a paragraph. Onboarding adds roughly **120 new
strings** (12 apps × ~5 screens × 2), every one of them app-specific prose that
is reused nowhere. Website guides add several times that, in long form.

Dropping that into `tools/ui-translations/<locale>.json` would take the 547
strings to ~700 and push the 47 locales currently sitting at 88/547 further
behind, while mixing prose into a file designed for reused UI labels.

**Proposal — prose lives with prose, and coverage is tiered honestly:**

- Guide copy uses the **website's per-locale copy mechanism** (`i18n/copy/<locale>/`),
  not the string-map pipeline. The generator emits the in-app subset (`intro` +
  `steps`) into the Swift bundles from there.
- **Tier 1 — reviewed by a human: the 9 locales the site already offers**
  (`en nl de fr es pt it mt hy`). These are the languages Tiko actually claims.
- **Tier 2 — machine-filled, marked as such: the other 45.** The translations-api
  README already points at Lezu for exactly this ("ready to POST to Lezu so it
  can fill the locales this tool has no file for").
- **Fall back to English per key, never per screen.** `TikoI18n` already does
  this. A half-translated onboarding shows English where a string is missing
  rather than a blank card.

**A decision is needed here:** do we ship machine translation for the 45, or do
we show English and only offer guides in the 9 we have written? Both are
defensible. Shipping 54 half-checked languages of parenting advice is a
different risk from shipping 9 good ones.

## Phasing

| Phase | What | Why this order |
| --- | --- | --- |
| **0** | Content shape, `packages/guides`, `tools/generate-guides.mjs` with `--check`. No UI. | Everything else depends on the shape being right. |
| **1** | `TikoGuideFlow` in TikoKit + pilot on **two** apps: **Yes-No** (simplest app there is) and **Globe** (the richest). | Two ends of the range is what proves "the setup can be the same". One app proves nothing. |
| **2** | Guide route on the website, rendered from the same content, for the same two apps. English first. | Proves one source really does feed both. |
| **3** | Roll out to the remaining apps, one per app, content written per app. | Mechanical once 1 and 2 hold. |
| **4** | Translation: Tier 1 by hand, Tier 2 by Lezu, coverage asserted per locale. | After the content has stopped moving. |

Blockers to clear along the way: register **Talk** and **Coloring** in
`TikoAppKey` and `source-en.json` (Phase 3), and land **TIKO-061** before
Phase 2.

---

## What this plan deliberately does not do

- **No Android or web-app renderer yet.** `tikokotlinkit` is two files; TIKO-025
  owns that migration. The guide content is platform-neutral JSON, so those
  renderers cost content nothing when they arrive.
- **No merge with `docsContent.ts`.** Those are developer docs. A caregiver
  guide and an architecture page are different documents for different readers.
- **No video, no interactive demo.** Static art per step, from the media library,
  the way every other picture in these apps arrives.
- **No forced tour on update.** `version` exists so a real change can re-show it,
  but bumping it is a decision, not a habit.

## Open questions

1. **Translation depth** — 9 reviewed languages, or 54 with machine fill marked?
   (See above. This one changes the shape of Phase 4.)
2. **Does onboarding ever show for a child?** Recommendation: no. It appears once
   on a fresh install, which is a grown-up setting the device up. If child mode
   is already active, skip it entirely and leave it in Settings.
3. **Route shape** — `/apps/<slug>/guide` or a top-level `/guides/<slug>`? The
   first keeps the app's material together; the second reads better as a
   documentation section.
